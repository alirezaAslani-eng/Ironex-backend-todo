یک ایده‌ای که دارم اینه که بک‌اند بر اساس پارامترهای Request بفهمه کاربر الان روی چه حالتی قرار داره و بر اساس اون، نحوه ارسال Eventها رو تغییر بده.

مثلاً وقتی برای گرفتن Order Book این Query رو می‌فرستم:

`settlementMode=1`

بک‌اند متوجه میشه که کاربر روی حالت معاملات ۱۰٪ هست و Eventهایی که برای این حالت نیاز به تغییر دارن رو با Payload مناسب ارسال می‌کنه.

برای حالت Demo هم می‌تونیم همین کار رو انجام بدیم؛ مثلاً وقتی:

`isDemo=true`

ارسال میشه، بک‌اند متوجه میشه کاربر در حالت Demo هست و Payload مربوط به Eventهای موردنیاز رو تغییر میده.

مزیت این روش اینه که مشکل Race Condition در کلاینت رو هم تا حد زیادی حل می‌کنه.

الان اگر بخوایم این حالت رو در کلاینت مدیریت کنیم، باید هم API رو Fetch کنیم و هم بعد از دریافت Response این کد رو اجرا کنیم:

```js
symbols.forEach((item) => {
  con.invoke("SubscribeToMarket", item.ticker, true, 0);
});
```

اینجا ممکنه بین دریافت Response از API و رسیدن `SubscribeToMarket` یا `Unsubscribe` به سرور یک Race Condition اتفاق بیفته. یعنی ممکنه Response رو دریافت کرده باشیم، ولی هنوز درخواست تغییر Subscription به سرور نرسیده باشه و در همین فاصله یک Event با اطلاعات اشتباه برای کلاینت ارسال بشه.

اما در روشی که پیشنهاد دادم، این مشکل وجود نداره؛ چون تغییر حالت و آماده شدن سیستم ارسال Event داخل همان API انجام میشه و API تا زمانی که این تغییرات در بک‌اند انجام نشده باشه، Response رو برنمی‌گردونه.

در نتیجه وقتی کلاینت Response رو دریافت می‌کنه، مطمئنه که بک‌اند هم از حالت جدید مطلع شده و Eventهای بعدی با اطلاعات درست ارسال میشن.

### 3. تسویه بدهی (Debt Settlement)

در توضیحات Feature این مورد را دیدم:

> «کاربر چند روز (مثلاً ۳ روز) فرصت دارد بقیه پول را واریز کند و دکمه "تسویه" را بزند تا جنس آزاد شود و به کیف پولش منتقل شود.»

گفته شده این endpoint نیاز هست :  `/api/v1/wallet/credit/contracts/{id}/settle`

**سؤالات:**

* آیا هر اکشنی که باعث بدهکار شدن کاربر میشود قرار داد اش میاد اینجا مثلا برای معاملات 10 درصد و اعتبار معاملاتی که کاملا از هم جدا هستن ولی در هر دو کاربر به ما بدهکار میشود.

### 4. دلیل Locked بودن دارایی‌ها

برای لیست دارایی‌های کاربر، نیاز دارم بدانم اگر یک Asset در وضعیت `Locked` قرار دارد، **دلیل Locked بودن آن چیست.**

و برای سفارش ها هم همین طور در لیست سفارش ها سفارش هایی هستن که ترکیبی از معاملات 10 درصد و اعتبار معاملاتی هست یا یکی از این دو تا این سافرش توی جدول باید چجوری معلوم بشه که کلن داستانش با بقیه سفارش ها فرق داره لغو کردنش شرایط خاص خودش را داره و بقیه مواردی که تفاوت ایجاد میکنه بین اون سفراش و بقیه سفارش ها مثلا بدهی کاربر و....

در حال حاضر فقط داشتن چیزی مثل:

```text
lockedBalance
```

برای UI کافی نیست، چون از روی آن نمی‌توانم به کاربر توضیح بدهم چرا دارایی او قفل شده است.

مثلاً ممکن است دلیل Locked بودن یکی از این موارد باشد:

* بدهی مربوط به Margin
* در انتظار تکمیل معامله
* در حال تسویه
* سایر محدودیت‌های سیستمی

```json
{
  "lockedBalance": 10000000,
  "lockReason": "MARGIN_DEBT"
}
```

- با این که اعتبار معاملاتی داشتم و `buyingPower` کافی داشتم باز اجازه معامله نمیداد ظاهرا داره از کیف پول اصلی کم میکنه سمت بک اند و اعتبار معاملاتی را در نظر نمیگیره چون موجودی کیف پولم برای معامله کافی نبود اما جمعش با اعتبار معاملاتی کافی بود.
