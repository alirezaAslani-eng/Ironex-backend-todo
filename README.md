
## تجمیع فرآیند احراز هویت سطح دو در یک API

- در حال حاضر فرآیند احراز هویت سطح دو از طریق دو API مجزا انجام می‌شود.
- این ساختار ممکن است باعث شود یکی از درخواست‌ها با موفقیت انجام شود و درخواست دیگر با خطا مواجه شود؛ در نتیجه بخشی از اطلاعات کاربر ذخیره شود و بخش دیگر ذخیره نشود.
- برای مثال، ممکن است بارگذاری تصویر کارت ملی با خطا مواجه شود، اما اطلاعاتی مانند آدرس و کد پستی با موفقیت ثبت شوند یا برعکس.
- این موضوع باعث پیچیده شدن مدیریت خطاها در سمت فرانت‌اند شده و احتمال بروز باگ و ناسازگاری داده‌ها را افزایش می‌دهد.
- پیشنهاد می‌شود کل فرآیند احراز هویت سطح دو از طریق یک Endpoint واحد (مانند `/api/v1/kyc/level2` یا `/api/v1/kyc/level2-info`) انجام شود تا عملیات به‌صورت یکپارچه مدیریت شده و در صورت بروز خطا، وضعیت درخواست نیز به‌صورت یکپارچه قابل مدیریت باشد.



## دریافت خطای ۴۲۹ هنگام ورود با رمز عبور



- هنگام ورود با رمز عبور، در برخی شرایط خطای **۴۲۹ (تعداد درخواست بیش از حد مجاز)** دریافت می‌شود.

- این مشکل بیشتر زمانی رخ می‌دهد که کاربر ابتدا درخواست ارسال کد یکبارمصرف را ثبت می‌کند، اما از ادامه فرآیند منصرف شده و تصمیم می‌گیرد با رمز عبور وارد شود.

- به نظر می‌رسد محدودیت تعداد درخواست مربوط به ارسال کد یکبارمصرف، روی API ورود با رمز عبور نیز اعمال می‌شود.

- لطفاً بررسی شود که آیا این رفتار مورد انتظار است یا در تنظیمات محدودیت تعداد درخواست‌ها مشکلی وجود دارد.



## مشکل مدیریت کش تصویر پروفایل کاربر



- هنگام دریافت تصویر پروفایل کاربر، هدرهای مربوط به مدیریت کش به‌درستی تنظیم نشده‌اند.

- پس از تغییر تصویر پروفایل، مرورگر دوباره درخواست دریافت تصویر را ارسال می‌کند، اما همچنان نسخه کش‌شده قبلی را نمایش می‌دهد.

- در حال حاضر برای رفع این مشکل مجبور شده‌ایم از هدرهای `no-cache` یا `no-store` استفاده کنیم که راهکار بهینه‌ای نیست.

- لطفاً هدرهای مربوط به مدیریت کش به‌گونه‌ای تنظیم شوند که پس از تغییر تصویر، نسخه جدید دریافت شود و در سایر مواقع مرورگر بتواند از کش به‌درستی استفاده کند.

- مسیر API: `/user/avatar-image`

## مشکل سوییچ به حساب حقیقی با API تغییر فضای کاری



- سوییچ از حساب حقوقی به حساب حقیقی (برگشت به حساب شخصی) با API `/switch-workspace` انجام نمی‌شود.

- زمانی که کاربر در یک حساب حقوقی قرار دارد و قصد بازگشت به حساب حقیقی خود را دارد، عملیات سوییچ با مشکل مواجه می‌شود.

- لطفاً بررسی شود که API `/switch-workspace` در سناریوی تغییر از حساب حقوقی به حساب حقیقی نیز به‌درستی عمل کند.

## مشکل ریسپانس اعضای شرکت در API لیست اعضا

- خروجی API `/workspaces/id/members` که اعضای یک شرکت را برمی‌گرداند، مشکل دارد.

- اگر یکی از اعضای شرکت هنوز ثبت‌نام نکرده باشد، شماره تماس آن عضو در ریسپانس به صورت `null` برگردد که رفتار مورد انتظار است.

- اما در صورتی که کاربر ثبت‌نام کرده باشد، شماره تماس آن کاربر همچنان در ریسپانس به صورت `null` برمی‌گردد.

- لطفاً بررسی شود که بعد از ثبت‌نام کاربر، اطلاعات شماره تماس به‌درستی در ریسپانس ارسال شود.



## عدم نمایش شرکت‌های حقوقی برای کارمند ایجادشده

- بعد از ایجاد یک کارمند با شماره **09216996841**، زمانی که با حساب آن کارمند وارد می‌شویم، در بخش حساب‌های حقوقی هیچ شرکتی نمایش داده نمی‌شود.

- انتظار می‌رود کارمند بتواند شرکت‌هایی که به آن‌ها اضافه شده است را مشاهده کند و امکان سوییچ به حساب حقوقی مربوطه را داشته باشد.

## عدم عملکرد ایونت تغییر قیمت بازار

- ایونت `marketPriceChanged` در حال حاضر ارسال نمی‌شود یا عملکرد درستی ندارد. لطفاً بررسی شود که این ایونت در تمامی سناریوهای مورد انتظار منتشر شود.



## عدم به‌روزرسانی لحظه‌ای پس از انجام معامله

- اگر سفارش فروش با قیمت بالاتر یا سفارش خرید با قیمت پایین‌تر ثبت شود، به‌گونه‌ای که معامله به نفع معامله‌کننده انجام شود، سرور هیچ ایونتی برای به‌روزرسانی لحظه‌ای (Real-time) ارسال نمی‌کند.

- پس از رفرش صفحه، مشخص می‌شود که سفارش با موفقیت انجام شده است، اما تا قبل از رفرش هیچ تغییری در داده‌ها اعمال نمی‌شود.

- در حال حاضر تنها بخشی که به‌صورت لحظه‌ای به‌روزرسانی می‌شود order book  هست.

## 403 بعد از سوییچ حساب حقوقی

- بعد از سوییچ به یک حساب حقوقی، برخی APIها مانند **Dashboard** و **Wallet** با وضعیت **403 Forbidden** پاسخ می‌دهند. لطفاً بررسی کنید که بعد از سوییچ، سطح دسترسی یا توکن به‌درستی به‌روزرسانی می‌شود.



## ریسپانس `/auth/login-cookie`

- ریسپانس API `/auth/login-cookie` حتماً باید فیلد `hasPassword` را برگرداند؛ فرانت‌اند برای تصمیم‌گیری در فرآیند ورود به این مقدار نیاز دارد.



## ایجاد حساب حقوقی برای کاربر احرازنشده

- توانستم برای شماره **09936460918**، با وجود اینکه احراز هویت نشده است، حساب حقوقی ایجاد کنم. لطفاً بررسی کنید که آیا این رفتار مطابق منطق سیستم است یا یک باگ محسوب می‌شود.



## افزودن کارمند با شماره مالک شرکت

- برای شرکت **دایان داده پرداز**، شماره **09936460918** که مالک شرکت است را مجدداً به‌عنوان کارمند اضافه کردم و سیستم این عملیات را پذیرفت.

- **نکته:** این شماره احراز هویت نشده است. آیا علت این رفتار، احراز نبودن شماره است یا این مورد نیز یک باگ محسوب می‌شود؟



## احراز هویت

- به یک API نیاز داریم که برای هر سطح KYC، قابلیت‌ها و محدودیت‌های آن سطح را به‌صورت یکجا برگرداند.

- برای مثال:

  - امکان برداشت

  - سقف برداشت

  - سقف واریز

  - سایر قابلیت‌ها و محدودیت‌های مربوط به همان سطح

- این کار باعث می‌شود فرانت‌اند نیازی به هاردکد کردن قوانین نداشته باشد.



## به‌روزرسانی SignalR کیف پول

- بعد از شارژ کیف پول، Hub مربوط به `/hubs/wallet` اطلاعات کیف پول را به‌روزرسانی نمی‌کند و تغییرات به کلاینت ارسال نمی‌شود.



## رفتار API `/merge-account`

- پیشنهاد می‌شود API `/merge-account` پس از انجام موفق عملیات، توکن‌های فعلی کاربر را باطل یا حذف کند تا فرانت‌اند کاربر را به صفحه ورود هدایت کرده و مجدداً احراز هویت انجام شود.



## اند پوینت های مورد نیاز برای داده چارت ها

- در حال حاضر به دو API مجزا نیاز داریم:

  1. روند تغییرات قیمت یک محصول در بازه زمانی.

  2. روند تغییرات سود و زیان (P&L) یا ارزش دارایی کاربر در بازه زمانی.

- همچنین اگر API دوم یک فیلد مانند `isInProfit` یا `isInLoss` نیز برگرداند، سمت فرانت می‌توانیم ساختار ساده‌تر و بهینه‌تری برای نمایش وضعیت سود و زیان داشته باشیم.
